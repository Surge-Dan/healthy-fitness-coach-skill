# Healthy Fitness Coach训练操作系统改造设计

- 日期：2026-08-30
- 状态：待用户评审
- 适用范围：独立Skill、训记连接器、训练报告与分享图工作流

## 1. 产品判断

Healthy Fitness Coach不再以“回答健身问题”为核心，而应成为一套个人训练决策系统：基于用户明确提供的背景、当前状态和训练记录，持续完成建档、计划、执行、记录、复盘与调整。

普通问答仍保留，但只作为低摩擦入口和知识补充。真正体现产品价值的是可执行方案、真实记录、可解释决策和可持续更新的本地资产。

一句话定位：

> 把“想练”转化为“开始练、持续记、定期复盘、基于证据调整”的个人训练操作系统。

## 2. 目标与非目标

### 2.1 产品目标

1. 用户第一次提出实质性训练需求时，用最少必要问题建立可用画像。
2. 将计划、今日训练、训练复盘、长期DNA、训记分析和分享输出编排为连续工作流。
3. 对需要执行或留存的任务，默认交付Markdown或相关本地资产，而不是只返回一段聊天文本。
4. 所有训练调整都采用“事实→判断→行动→验证”结构，并留下决策记录。
5. 通过真实训练反馈逐步提高个性化程度，不根据一次对话制造“训练DNA”。

### 2.2 非目标

- 不取代医生、物理治疗师、注册营养师或线下教练的诊断和专项评估。
- 不把每个简单问题强制升级为完整问卷。
- 不用单一分数伪装精确诊断，不输出无法解释的黑箱建议。
- 不以聊天轮数、回答长度或图表数量作为产品成功指标。
- 不把用户必须使用训记、上传照片或记录饮食作为前提。

## 3. 核心用户任务

系统围绕五类任务工作：

| 场景 | 用户真实目标 | 核心交付 |
| --- | --- | --- |
| 开始训练 | 从模糊愿望变成可执行周期 | 训练画像、当前计划、记录指标 |
| 执行训练 | 知道今天该怎么练并能完成 | 今日训练卡、最低任务、训练后记录 |
| 复盘调整 | 判断什么有效、哪里需要调整 | 周/月复盘、决策日志、下一周期 |
| 长期训练系统 | 累积个人规律而不是反复从零咨询 | 训练DNA、证据台账、版本变化 |
| 记录与分享 | 看懂阶段成果并生成可分享内容 | Markdown报告、趋势面板、分享图 |

知识问答、动作解释和博主观点属于支持能力，不是独立产品核心。

## 4. 交互原则：渐进建档，不做全量盘问

### 4.1 三层用户状态

系统维护三类状态：

1. **稳定画像**：年龄段、目标、经验、场地、器械、每周时间、安全限制和长期偏好。
2. **当前状态**：今日睡眠、压力、疲劳、疼痛、时间和临时器械条件。
3. **训练证据**：训练记录、完成率、动作表现、RPE/RIR、有氧数据、恢复反馈和数据缺失。

稳定画像只在背景变化时更新；当前状态按次使用；训练证据随训练记录增量更新。

### 4.2 场景所需字段

每种任务只要求会改变安全性或方案结构的字段：

| 任务 | 必要字段 |
| --- | --- |
| 概念问答 | 无；若涉及个人疼痛则进入安全分流 |
| 制定周期计划 | 安全筛查、目标、经验、频率、单次时长、场地/器械、动作限制 |
| 今日训练 | 当前计划或训练目标、今日时长、睡眠/疲劳、当前不适、可用器械 |
| 训练复盘 | 分析范围、训练记录、当前目标、记录完整度 |
| 训练DNA | 至少多个可比较训练窗口、结果字段、恢复或依从反馈 |
| 分享图 | 真实照片或真实训练数据、输出比例；仅在多个方向都合理时询问风格 |

非安全字段缺失时允许保守默认，但必须把默认项和最值得补充的一项写入交付物。

### 4.3 提问规则

- 优先复用用户已经说过或档案中已有的信息，不重复追问。
- 首次计划任务可以一次性发送结构化建档问题，减少来回轮次。
- 后续交互只询问变化量，例如今日状态或新增限制。
- 一次最多追问一组同类问题；简单知识问题直接回答。
- 红旗症状优先于所有画像、报告和图片任务。

## 5. 任务路由与默认交付

### 5.1 路由规则

| 请求类型 | 默认模式 |
| --- | --- |
| 定义、原理、单个动作提示 | 简短对话 |
| 红旗症状或即时一般不适 | 对话式安全分流 |
| 今日训练、逐组跟练 | 对话＋可选今日训练卡 |
| 周期计划、建档、计划调整 | Markdown资产 |
| 周/月/年度复盘、训练数据分析 | Markdown报告＋按需图表 |
| 训记趋势 | Markdown报告＋本地趋势面板 |
| 建立长期训练系统 | 多文件资产包 |
| 分享或社交发布 | 图片＋简短数据说明 |

### 5.2 Markdown优先规则

以下任务默认生成可保存的Markdown，而不是等待用户再次要求：

- 完整周期计划；
- 周/月/年度复盘；
- 平台期或计划调整分析；
- 训练档案和训练DNA；
- 训记数据分析；
- 需要后续继续更新的训练方案。

具备写入工具时，文件保存到`fitness-reports/`并避免覆盖已有文件；没有写入工具时，直接返回完整Markdown。简单知识问答和即时安全分流不强制生成文件。

## 6. 五个决策引擎

### 6.1 安全门

先识别红旗、特殊人群、近期手术/急性外伤和进行性症状：

- 红旗：停止训练处方，建议及时获取专业评估；
- 一般不适：进入保守调整，降低负荷、幅度或更换无痛变式；
- 无明显风险：进入对应训练流程。

安全门不输出诊断结论。

### 6.2 信息充分度引擎

按场景检查必要字段，结果只有三类：

- `ready`：信息足够，直接执行；
- `ask`：缺少会改变安全性或方案结构的字段，集中追问；
- `assume`：只缺少非关键字段，采用保守默认并显式标注。

不使用无法解释的综合分数代替字段判断。

### 6.3 计划编排引擎

输入：用户画像、目标、频率、时长、器械、恢复与偏好。

输出：训练分化、每周结构、动作模式、组次/时长、RPE/RIR、休息、替代动作、最低任务、进阶规则、降级规则和复盘日期。

基本约束：

- 每周次数不得超过用户可稳定执行的频率；
- 单次内容必须能在声明时长内完成；
- 新手优先稳定动作、频率和记录习惯；
- 阻力、有氧和恢复按主目标编排，不互相混算；
- 每个计划只选择1～3个本周期验证指标。

### 6.4 今日状态引擎

根据当前计划、睡眠、压力、疲劳、疼痛和可用时间输出三类行动：

- 正常执行；
- 降级执行：减少组数、降低强度、缩短时长或使用替代动作；
- 停止处方：出现红旗或明显恶化。

输出必须包含最低任务版本和训练后需要回填的字段。

### 6.5 复盘调整引擎

固定采用“事实→判断→行动→下一次验证”：

1. 汇总完成率、训练频率、部位覆盖、动作表现、有氧剂量、恢复和数据质量；
2. 只比较同动作或相近条件，不跨器械、跨单位制造趋势；
3. 一次最多调整1～2个可记录变量；
4. 每次调整写明预期影响、回退条件和复核日期；
5. 数据不足时保持未知，不生成假进步、假偏好或假平台期。

典型规则：

- 计划完成率持续偏低：先降低复杂度、时长或频率；
- 同动作在相近RPE/RIR下表现提高：允许按既定规则进阶；
- 多次可比较表现下降且恢复较差：考虑减量或延长恢复；
- 单次状态下降：记录观察，不重写整个计划；
- 一般不适：先修改一个训练变量并设置复评条件。

## 7. 训练DNA的产品定义

训练DNA不是即时标签，而是经过验证的长期假设集合：

> 初始画像→训练计划→执行记录→周期复盘→重复验证→训练DNA。

每条DNA结论必须包括：

- 结论内容；
- 数据范围；
- 支持证据；
- 反证或混杂因素；
- 置信度；
- 下一次验证条件；
- 版本变化。

单次反馈只能形成低置信度观察；缺少表现、恢复或结果字段时不能升级为高置信度规律。

## 8. 长期资产模型

### 8.1 默认资产

| 文件 | 作用 |
| --- | --- |
| `ATHLETE_PROFILE.md` | 稳定画像、安全边界、目标和现实约束 |
| `CURRENT_PROGRAM.md` | 当前周期、训练结构、进阶和降级规则 |
| `DECISION_LOG.md` | 每次计划变更的事实、推断和验证条件 |
| `WEEKLY_REVIEW.md` | 完成情况、表现、恢复和下周重点 |

### 8.2 条件资产

| 文件 | 生成条件 |
| --- | --- |
| `TODAY_WORKOUT.md` | 用户需要保存或打印今日训练卡 |
| `TRAINING_DNA.md` | 已有多个可比较训练窗口 |
| `PROGRESS_LEDGER.csv` | 用户愿意持续记录或已连接训记 |
| `EXERCISE_PLAYBOOK.md` | 需要维护动作替代、不适变式或常用提示 |
| `DNA_EVIDENCE.jsonl` | DNA进入持续版本管理 |
| `DNA_CHANGELOG.md` | DNA发生升级、降级或撤销 |

资产之间使用相同的用户目标、周期版本和日期范围，避免互相矛盾。

## 9. 训记数据闭环

训记是增强数据源，不是产品使用前提。

工作流：

1. 用户明确表示连接训记；
2. 用户在私密会话中提供官方接口说明和自己的API Key；
3. 系统按最小日期范围读取并优先使用本地缓存；
4. 对数据进行日期、单位、记录类型、重复项和缺失项校验；
5. 生成报告、趋势、复盘或DNA候选规律；
6. 只有用户要求且确认预览后，才按训练ID写回；
7. Key不进入回复、报告、仓库、日志或训练资产。

读取失败时允许用户粘贴导出文本或使用手工日志，且报告必须标注数据边界。

## 10. 报告与分享层

报告层负责解释训练，分享层负责表达训练，两者不能修改事实。

### 10.1 报告

周/月/年度报告至少说明：训练天数、有效记录、训练量或组数、有氧时长、部位覆盖、主动作表现、完成率和数据质量。图表只能使用真实记录。

### 10.2 分享图

- 有照片：提取视觉信息，生成拼贴、手绘、漫画、双色小志等设计方向；
- 无照片：使用真实训练数据生成信息图或抽象数据艺术；
- 派生艺术层不得生成虚假成绩、数字、图表或Logo；
- 中文文字、训练数据和最终排版由本地合成器处理；
- 支持1:1、9:16和3:4。

## 11. 数据流

1. 用户请求进入任务路由；
2. 安全门判断是否可以继续；
3. 读取已有画像和当前计划；
4. 信息充分度引擎决定直接执行、追问或保守默认；
5. 对应场景引擎生成计划、今日训练、复盘或分享方案；
6. 默认交付Markdown或场景资产；
7. 训练后收集最少反馈；
8. 更新训练记录、复盘和决策日志；
9. 达到证据门槛后更新训练DNA；
10. 下一次请求优先复用已有状态。

## 12. 异常和降级

- 没有写入工具：在对话中返回完整Markdown，不声称已保存文件。
- 没有网络或训记连接失败：降级为用户粘贴导出文本或手工日志。
- 数据日期缺失或单位混合：标记无效或未知，不参与趋势结论。
- 用户拒绝建档：仍可提供通用保守建议，但明确个性化边界。
- 用户信息发生冲突：以最新明确陈述为准，并在决策日志记录变化。
- 图片生成工具不可用：输出可执行视觉Brief和本地合成方案，不伪装成已生成图片。
- 任何红旗：停止计划、报告优化和训练推进。

## 13. 产品指标

### 13.1 北极星指标

用户在一个训练周期内完成计划训练，并基于真实记录完成至少一次有效复盘。

### 13.2 辅助指标

- 首次画像完成率；
- 首个周期计划启动率；
- 训练记录完整率；
- 4周计划完成率；
- 最低任务挽回率；
- 完成复盘后进入下一周期的比例；
- 有证据支持的计划调整比例；
- 训记读取的缓存命中率和数据有效率；
- 红旗场景正确停止训练处方的覆盖率。

报告数量、聊天轮数和图片数量不作为核心成功指标。

## 14. 验收场景

1. 用户问“RIR是什么意思”：直接简短回答，不强制建档或生成文件。
2. 新手要求每周3次计划：只追问缺失的安全和计划关键字段，生成画像与当前计划Markdown。
3. 已建档用户说“今天练胸”：复用当前计划，只补今日状态，输出正常、降级或停止方案。
4. 用户睡眠不足：提供降级训练和最低任务，不直接把一次睡眠不足解释为长期恢复问题。
5. 用户提供4周日志：输出数据质量、事实、有限判断、1～2项调整和下一次验证条件。
6. 用户只有一次训练：不得生成确定训练DNA。
7. 用户要求年度训记分析：优先缓存读取，验证日期和单位，输出Markdown报告与趋势面板。
8. 用户要求写回训记：必须先展示预览并取得确认，保留训练ID和训练时间。
9. 用户上传照片：先提供或自动选择适合输入的设计配方，最终数字全部来自真实记录。
10. 用户出现胸痛、异常气短、晕厥或进行性无力：停止训练处方并建议专业评估。

## 15. 测试要求

### 15.1 单元测试

- 场景路由；
- 必要字段判断；
- 保守默认；
- 计划编排约束；
- 今日状态分流；
- 调整规则；
- DNA置信度；
- Markdown资产路径和不覆盖规则。

### 15.2 Gherkin测试

覆盖首次建档、今日训练、一般不适、红旗、手工日志、训记读取、写回确认、年度报告和分享图完整流程。

### 15.3 对抗测试

- 用户前后信息冲突；
- 缺失日期、重复记录、混合单位；
- 一次训练要求高置信度DNA；
- 训练下降但恢复数据缺失；
- 要求使用他人固定课表；
- API Key出现在输入、错误和日志边界；
- 图片中要求生成虚假成绩；
- 简单问题被错误升级为长问卷。

### 15.4 质量指标

- 所有建议能追溯到用户事实、确定性规则或明确证据；
- 所有计划满足频率、时长、器械和安全限制；
- 所有调整都有回退条件和复核日期；
- 所有未知数据保持未知；
- 所有持久资产不包含API Key；
- 简单任务不产生多余文件和盘问。

## 16. 兼容与迁移原则

现有知识库、训练DNA引擎、训记连接器、Markdown模板、趋势面板和视觉编译器继续复用。改造重点是统一入口和状态流，而不是重新实现所有功能。

现有`ATHLETE_PROFILE.md`、`CURRENT_PROGRAM.md`、`DECISION_LOG.md`和`TRAINING_DNA.md`保持兼容；新增今日训练资产和任务状态时，不改变已有文件的事实/推断边界。

## 17. 最终验收定义

当用户完成一次“建档→计划→今日训练→记录→复盘→调整”流程后，系统应留下可继续使用的本地资产；下一次交互能够读取这些状态，不重复从零询问，并能说明每次建议基于什么事实、改变了什么变量、下一次如何验证。

达到这一点，Healthy Fitness Coach才与普通健身问答产生本质区别。
